# CheckStock

МВП ERP для учёта товаров и складов. На первом этапе реализованы два справочника:

- **Товары:** ID, артикул (`sku`), наименование (`name`).
- **Склады:** ID, наименование (`name`).

Для обоих справочников предусмотрены создание, список, получение по ID,
редактирование и удаление через REST API. Простой веб-интерфейс использует этот же API.

Стек: Python 3.14+, FastAPI, PostgreSQL, SQLAlchemy 2, Alembic, HTML/CSS/JavaScript.

## Настройка и запуск

### Docker Compose

При установленном Docker с Compose из корня проекта:

```sh
docker compose up --build
```

Создавать `.env` для этого не нужно. По умолчанию имя БД, пользователь и пароль —
`checkstock`, порт приложения — `8000`.

При сборке образа `uv sync --locked --no-dev` устанавливает зависимости по `uv.lock`
в `/app/.venv`. Alembic и Uvicorn запускаются напрямую из этого окружения.

Порядок запуска:

1. PostgreSQL создаёт пользователя и БД с заданными параметрами.
2. Compose ждёт готовности PostgreSQL через `healthcheck`.
3. Контейнер приложения выполняет `alembic upgrade head`.
4. Если миграции успешны, запускается Uvicorn; при старте приложения заполняются типы документов.

Интерфейс: <http://localhost:8000/>, Swagger: <http://localhost:8000/docs>.

Создание БД и пользователя выполняет [официальный образ PostgreSQL](https://hub.docker.com/_/postgres)
при первом запуске с пустым хранилищем. Данные сохраняются в volume `postgres_data`.
Команда `docker compose down` останавливает проект и сохраняет данные.

Для своих параметров скопируйте `.env.example` в `.env` и измените
`POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `APP_PORT`.
`DATABASE_URL` для контейнера формируется в Compose из этих параметров,
локальное значение из `.env` не используется. Инициализационные параметры
PostgreSQL применяются только к пустому хранилищу: изменение `.env` не меняет
пароль или имя уже созданной БД.

### Локальный запуск без Docker

Нужны uv, Python 3.14+ и PostgreSQL. Из корня проекта:

```sh
uv sync
source .venv/bin/activate
cp .env.example .env
```

В `.env` укажите параметры своей базы PostgreSQL:

```dotenv
APP_NAME=CheckStock
DATABASE_URL=postgresql+psycopg://checkstock:checkstock@localhost:5432/checkstock
```

Имя пользователя, пароль и имя базы в примере — локальные значения-заглушки.
Настройки можно также передать через переменные окружения; они имеют приоритет над `.env`.

Создайте БД и пользователя в PostgreSQL, затем примените миграции и запустите сервер:

```sh
alembic upgrade head
uvicorn app.main:app --reload
```

- Интерфейс: <http://127.0.0.1:8000/>
- Swagger UI: <http://127.0.0.1:8000/docs>
- OpenAPI: <http://127.0.0.1:8000/openapi.json>

До создания таблиц приложение не завершит запуск: инициализация справочника
типов документов требует готовой схемы PostgreSQL.

## API

| Метод | Товары | Склады | Действие |
| --- | --- | --- | --- |
| POST | `/api/v1/goods` | `/api/v1/warehouses` | Создать |
| GET | `/api/v1/goods` | `/api/v1/warehouses` | Получить список |
| GET | `/api/v1/goods/{id}` | `/api/v1/warehouses/{id}` | Получить по ID |
| PATCH | `/api/v1/goods/{id}` | `/api/v1/warehouses/{id}` | Изменить переданные поля |
| DELETE | `/api/v1/goods/{id}` | `/api/v1/warehouses/{id}` | Удалить |

Создание товара:

```json
{"sku": "SKU-001", "name": "Тестовый товар"}
```

Создание склада:

```json
{"name": "Основной склад"}
```

Частичное изменение товара:

```json
{"name": "Новое наименование"}
```

Списки возвращаются целиком массивом, упорядоченным по ID.

Артикул обязателен, уникален с учётом регистра и ограничен 64 символами.
Наименование обязательно и ограничено 255 символами. Пробелы по краям удаляются;
пустые строки, `null` и неизвестные поля не принимаются. В PATCH нужно передать
хотя бы одно поле. Наименования товаров и складов могут повторяться.

Коды ответов: `201` при создании, `200` при чтении и изменении,
`204` при удалении, `404` для отсутствующей записи, `409` для занятого артикула,
`422` при ошибке входных данных.

## Документы и остатки

| Метод | Путь | Действие |
| --- | --- | --- |
| GET | `/api/v1/document-types` | Поддерживаемые типы документов |
| POST | `/api/v1/documents` | Создать и провести документ |
| GET | `/api/v1/documents` | Получить журнал документов |
| GET | `/api/v1/documents/{id}` | Получить документ с товарами |
| DELETE | `/api/v1/documents/{id}` | Создать обратный документ и отменить исходный |
| GET | `/api/v1/stock-balances` | Доступное количество по товарам и всем складам |
| POST | `/api/v1/reserves` | Увеличить резерв товара на складе без документа |
| POST | `/api/v1/reserves/release` | Снять часть или весь резерв товара на складе |
| POST | `/api/v1/documents/{id}/delivered` | Установить или снять доставку перемещения/отправки |

Изменение проведённых документов не предусмотрено; маршрутов PUT/PATCH для них нет.

Поддерживаемые коды типов:

| Код | Наименование | Склад-источник | Склад-получатель |
| --- | --- | --- | --- |
| `shipment` | Отправка | Обязателен | `null` |
| `shipment_fbo` | Отправка на ФБО | Обязателен | `null` |
| `receipt` | Приход | `null` | Обязателен |
| `transfer` | Перемещение | Обязателен | Обязателен, отличается от источника |

`GET /document-types` возвращает фиксированные коды и наименования без обращения
к БД. При запуске приложения через FastAPI lifespan функция
`app/db/initial_data.py` добавляет все отсутствующие типы в `documents_types` одной
транзакцией. Повторный запуск не создаёт дубликаты и не меняет существующие записи.
Метод создания документа справочник не заполняет. Автоматического создания таблиц нет.

Все примеры ниже — тела `POST /api/v1/documents`. ID товаров и складов должны
существовать. Поля складов, которые не нужны операции, можно опустить или передать
как `null`; передавать в них ID запрещено.

Приход:

```json
{
  "document_type": "receipt",
  "target_warehouse": 1,
  "items": [
    {"good_id": 1, "quantity": 10},
    {"good_id": 2, "quantity": 5}
  ]
}
```

Отправка:

```json
{
  "document_type": "shipment",
  "source_warehouse": 1,
  "items": [{"good_id": 1, "quantity": 2}]
}
```

Отправка на ФБО из той же формы с галочкой:

```json
{
  "document_type": "shipment",
  "fbo": true,
  "source_warehouse": 1,
  "items": [{"good_id": 1, "quantity": 2}]
}
```

В этом случае документ сохраняется с типом `shipment_fbo`. Можно также явно
передать `"document_type": "shipment_fbo"`. Флаг `fbo: true` для прихода и
перемещения запрещён.

Перемещение:

```json
{
  "document_type": "transfer",
  "source_warehouse": 1,
  "target_warehouse": 2,
  "items": [{"good_id": 1, "quantity": 3}]
}
```

В документе нужен хотя бы один товар. ID и количества — положительные целые
числа; дроби, строки и булевы значения вместо чисел не принимаются.
Повторяющиеся товары суммируются в одну строку до проверки
доступного количества. Нулевые и отрицательные количества в запросе создания
запрещены; отрицательные движения создаёт только сервис отмены.

### Проведение и ошибки

`InventoryService` проверяет сочетание складов, FBO и доступное количество.
Существование товаров и складов обеспечивают внешние ключи БД без предварительных
запросов из сервиса. Диапазон `INTEGER` контролирует PostgreSQL; ошибка выхода
за диапазон возвращается как `422` с кодом `numeric_value_out_of_range`.
Документ, строки товаров
и изменения всех остатков записываются одной транзакцией. При ошибке все изменения
откатываются, включая новые строки остатков.

Сервис использует PostgreSQL `INSERT ... ON CONFLICT DO NOTHING` для отсутствующих
остатков и `SELECT ... FOR UPDATE` для проверки и изменения остатков. Строки
блокируются в едином порядке `(good_id, warehouse_id)`. Проверка доступного
количества выполняется после блокировки, чтобы два запроса не списали один товар
одновременно.

Отправка, отправка на ФБО и перемещение требуют достаточного `available` на
складе-источнике. При недостаче возвращается `409` с деталями всех недостающих
позиций, например:

```json
{
  "detail": "Недостаточно доступного товара на складе",
  "code": "insufficient_stock",
  "context": {
    "shortages": [
      {"good_id": 1, "warehouse_id": 1, "requested": 3, "available": 2}
    ]
  }
}
```

Ссылка на отсутствующий товар или склад даёт `409` с кодом `reference_conflict`;
недопустимые параметры — `422`.
Конфликт параллельных транзакций, который PostgreSQL прервал, возвращается как
`409` с кодом `concurrent_operation`; такой запрос можно повторить.
Удаление товара или склада, на который ссылаются движения или остатки, блокируется
внешним ключом и возвращает `409`.

### Отмена и журнал

`DELETE /api/v1/documents/{id}` не удаляет строки из БД. Он возвращает `200`
с новым документом того же типа, исходными складами, `is_deleted: true`,
`reversal_of_id` исходного документа и отрицательными количествами.
Так отмена отправки возвращает товары, а отмена прихода списывает их.
Отмена перемещения возвращает товар источнику. У получателя он списывается
только если перемещение было подтверждено как доехавшее.

При отмене проверка доступного количества пропускается: `stock` и `available`
могут стать отрицательными. Резерв не изменяется. Отменить один документ дважды
или отменить сам документ отмены нельзя (`409`).

В ответах документов поле `is_cancelled` показывает, отменён ли оригинал,
а `reversal_id` содержит ID его обратного документа. Флаг `is_deleted` принадлежит
обратному документу; оригинал сохраняется без изменения. Ответы также содержат
дату, склады и строки товаров с ID, артикулом, наименованием и количеством.

Журнал возвращается целиком и сортируется по ID от новых к старым. Он принимает
необязательный фильтр `document_type` и `include_reversals` (по умолчанию `true`).
При `include_reversals=false` скрываются обратные документы, отменённые оригиналы
остаются с `is_cancelled: true`.

### Таблица доступных остатков

`GET /api/v1/stock-balances` возвращает массив по всем товарам:

```json
[
  {
    "good_id": 1,
    "sku": "SKU-001",
    "name": "Тестовый товар",
    "total_available": 8,
    "total_reserve": 2,
    "total_in_transit": 3,
    "in_transit_fbo": 1,
    "in_transit_fbs": 1,
    "in_transit_transfer": 1,
    "warehouses": [
      {"warehouse_id": 1, "name": "Основной склад", "available": 5, "reserve": 2},
      {"warehouse_id": 2, "name": "Второй склад", "available": 3, "reserve": 0}
    ]
  }
]
```

Список включает товары без движений и все существующие склады. Если строки
остатка нет, доступное количество равно `0`. Если складов нет, `warehouses`
пуст, а `total_available` равен `0`. Отрицательные значения после отмены
сохраняются в ответе.

Чтение выполняется одним `SELECT`: все товары соединяются со всеми складами
и соответствующими остатками. `LEFT JOIN` сохраняет товары без движений и склады
без остатка; `COALESCE` заменяет отсутствующие количества на `0`. В Python поля
строки читаются по именам, строки группируются по товару и считается итог из
показанных складов. Один запрос читает согласованный снимок БД, отдельный
`REPEATABLE READ` для этого метода не требуется.

«В пути» вычисляется в том же запросе как сумма товаров в исходных, неотменённых
перемещениях между ФФ (`transfer`), отправках на ФБО (`shipment_fbo`) и клиенту
по FBS (`shipment`) с `is_delivered = false`. Ответ содержит отдельные поля
`in_transit_transfer`, `in_transit_fbo`, `in_transit_fbs` по этим направлениям.
Их сумма — `total_in_transit`. В интерфейсе показаны три отдельные колонки;
в `warehouses` поля in_transit нет. Все показатели вычисляются в одном SELECT
и не умножаются на число складов. Доставленные и отменённые документы исключаются
как из общего количества, так и из соответствующего направления.

Создание перемещения списывает товар с источника, не пополняя получателя.
Товар становится доступен на складе-получателе только после подтверждения
«Товары доехали» внутри документа.

### Резерв без документа

`POST /api/v1/reserves`:

```json
{"good_id": 1, "warehouse_id": 1, "quantity": 2}
```

Количество добавляется к существующему резерву, а не заменяет его. Сервис
блокирует строку остатка и сравнивает
quantity с актуальным available. При нехватке возвращается `409` без изменений.
При успехе возвращаются good_id, warehouse_id, stock, reserve и available.
Записи documents_moves и stock_moves не создаются. Отправка и перемещение
по-прежнему проверяют только available и не используют зарезервированные товары.

Для снятия части или всего резерва используется `POST /api/v1/reserves/release`
с такой же структурой тела:

```json
{"good_id": 1, "warehouse_id": 1, "quantity": 2}
```

Количество должно быть положительным целым и не превышать текущий reserve
выбранного товара на выбранном складе. Сервис проверяет это под блокировкой
строки остатка. При превышении возвращается `409` с кодом `insufficient_reserve`.
Резерв уменьшается, available пересчитывается, stock сохраняется. Снятие возможно
и при отрицательном available. Ответ — обновлённые stock, reserve, available
и ID товара/склада. Документ или запись движения не создаются.

### Подтверждение и снятие доставки

`POST /api/v1/documents/{id}/delivered` принимает:

```json
{"is_delivered": true}
```

Это подтверждение всего документа. `{"is_delivered": false}` снимает отметку
и возвращает товары в общий показатель «В пути». Запрос без тела по-прежнему
означает подтверждение. Допустимы только исходные, неотменённые документы
`transfer`, `shipment_fbo`, `shipment`. Повтор текущего значения ничего не меняет.

У перемещения подтверждение увеличивает stock и available склада-получателя,
а снятие отметки уменьшает их на количества документа. При снятии допустим
отрицательный остаток, даже если товар уже израсходован или зарезервирован.
У отправок ФБО/FBS переключение влияет только на «В пути».

Резерв не меняется. Новых документов, движений или событий истории доставки нет;
дата доставки не хранится. Отметка документа и складские изменения фиксируются
одной транзакцией. Все документы подчиняются одинаковым правилам.
